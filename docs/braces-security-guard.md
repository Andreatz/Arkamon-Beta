# Mitigazione locale degli annidamenti braces

Il 12 ottobre 2026 l'advisory [GHSA-vfj7-8cjw-p6xm](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm) riguarda braces fino a 3.0.3 e non indica una versione corretta. La [discussione nel repository di braces](https://github.com/micromatch/braces/issues/84) conferma l'assenza di una release di correzione. Tailwind 3 resta in uso; questa modifica applica una mitigazione locale del problema di esaurimento dello stack.

Il postinstall esegue scripts/harden-build-dependencies.mjs. Prima di scrivere, controlla ogni copia di braces registrata nel lockfile: versione 3.0.3 e SHA-256 dei cinque file originali coinvolti. Una sorgente diversa, una versione diversa o una patch parziale interrompono l'installazione. La patch è deterministica e una seconda esecuzione non scrive nulla. Le dipendenze di sviluppo effettivamente omesse da un'installazione di sola produzione non richiedono una patch; una copia presente deve superare tutti i controlli.

Il controllo del pattern è iterativo e viene eseguito prima del parser: lunghezza massima 10.000 caratteri e annidamento effettivo massimo 64, rispettando escape, apici e parentesi quadre. Le funzioni compile, stringify ed expand controllano anche gli AST ricevuti direttamente, prima della ricorsione: profondità massima 128, budget massimo 20.000 nodi e rifiuto di cicli o catene parent incontrollate. flatten riceve un controllo iterativo analogo sugli array. Il rifiuto produce un RangeError con codice BRACES_COMPLEXITY_LIMIT; il chiamante resta responsabile di gestire gli errori ricevuti.

Questi limiti restringono gli input patologici. La mitigazione riguarda lo stack e non promette un limite generale a ogni possibile espansione combinatoria di un glob. Non cambia il numero di versione npm e non nasconde l'advisory. Il 12 ottobre l'audit completo mantiene **cinque high**, tutti nella catena braces/chokidar/fast-glob/micromatch/tailwindcss; l'audit delle dipendenze di produzione restituisce **zero**. Nessuna segnalazione critica resta nei due audit.

Eseguire npm run test:security dopo l'installazione. Le prove verificano input da 10.000 annidamenti, AST costruiti direttamente, cicli nei nodi e nei parent, array profondi, i limiti, globs e intervalli normali, ripresa del processo dopo un errore gestito, installazione iniziale, idempotenza e rifiuto di sorgenti/versioni inattese. L'installazione con ignore-scripts evita il postinstall: in quel caso eseguire esplicitamente lo script prima di avviare la toolchain. Una futura release upstream richiede una revisione della patch e dei suoi hash.
